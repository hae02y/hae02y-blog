# hae02y 블로그 글쓰기 / 윤문 스킬

hae02y(정해영) 기술 블로그(blog.hae02y.me)의 글을 **작성**하거나 **윤문(다듬기)**할 때 이 규칙을 따른다.
작성/윤문 모두 **저자의 목소리와 의도를 보존**하는 것이 최우선이다. 내용을 지어내거나 사실·코드를 임의로 바꾸지 않는다.

## 사용법
- `작성`: 메모·개요를 받아 아래 구조로 초안 작성 (frontmatter 포함)
- `윤문`: 기존 초안을 아래 규칙에 맞게 다듬기 (내용 보존, 문장·맞춤법·흐름만 개선)

둘 중 어느 쪽인지 애매하면 사용자에게 먼저 묻는다.

## 문체 규칙 (TECH 블로그 기본)
- **평서체 문어체**가 기본: "~한다", "~이다", "~비교한다", "~통과한다". 과한 경어체·감탄·이모지 지양.
- **1인칭은 필요할 때만 자연스럽게**: "나는", "내가" — 개인 경험·판단을 말할 때. 남발하지 않는다.
- 교과서식 장황한 이론 설명 금지. **실무 적용 중심, 간결하게.**
- 문장은 짧고 명확하게. 한 문장에 한 가지 생각.

## 도입부
- **실무 상황 / 개인적 계기**에서 출발한다. 예: "실무에서 N+1이 발생하여", "레거시를 마이그레이션하던 중", "왜 이렇게 동작하는지 궁금했다".
- frontmatter 바로 아래 **도입 1~2문장**으로 시작 (바로 `##` 섹션으로 들어가지 않음).
- "이 글에서는 ~를 다룬다" 식으로 글의 범위를 1문장 예고하면 좋다.

## 본문 구조
- **`##` 섹션 중심** (필요하면 `###` 소섹션). `#`는 쓰지 않는다(제목은 frontmatter title).
- **코드/예시 먼저 → 짧은 설명 뒤에.** "결과를 보면~", "이로 인해 발생하는 쿼리는 다음과 같다." 패턴.
- 번호 리스트(1·2·3), 비교표(장단점) 적극 활용.
- **기술 용어는 백틱**으로 감싼다: `JPA`, `Fetch Join`, `N+1`, `GIL`, `LAZY`.
- 이미지 캡션은 짧게: `![조회 결과](url)`.
- 참고 링크는 본문에 인라인으로: `[참고: 토스](url)`.

## 이미지 수집·캡처 (작성 시)
글은 글자만 있으면 밋밋하다. 주제에 맞는 **관련 이미지를 적극적으로 마련**한다. 우선순위:

1. **직접 캡처 (최우선)** — 도구·라이브러리·명령어 글이면 **실제로 설치·실행해 보고 그 화면을 캡처**한다.
   - 예: `REA`(Reverse Engineer Anything) 글이면 REA를 실제 설치→실행→분석하는 화면을 단계별로 캡처해 넣는다. "설치 화면 / 명령 실행 / 결과" 흐름.
   - 터미널 출력, 에러 화면, 결과 그래프 등도 직접 재현해 캡처.
   - 캡처는 브라우저 자동화(claude-in-chrome) 또는 로컬 실행 후 스크린샷으로 얻는다.
   - **장점: 저작권 문제 없음 + 진짜 사용 화면이라 신뢰도 높음.** 가능하면 항상 이 방식.
2. **공식 자료** — 공식 문서/레포의 다이어그램·스크린샷. **출처를 캡션이나 인라인 링크로 표기**.
3. **오픈 라이선스 이미지** — CC 등 재사용 허용되는 것만, 출처 표기.

**금지**: 라이선스 불명확한 이미지를 무단으로 가져와 게시. 저작권 있는 사진/도표를 그대로 복제 게시.

**처리 흐름**: 이미지 확보 → `/admin` 업로드(또는 Vercel Blob)로 올려 URL 획득 → 본문에 `![설명](url)` 삽입. 캡션은 짧게.
다이어그램은 가능하면 이미지 대신 `mermaid` 코드블록으로(버전관리·수정 쉬움).

작성 전에 "이 글에 어떤 이미지가 필요한가(직접 캡처할 것 / 찾을 것)"를 먼저 정리하고, 직접 캡처가 가능한 건 사용자에게 **실제로 해보고 캡처해도 되는지** 확인한 뒤 진행한다.

## 설명 패턴
- **"하지만" 패턴**: 장점·동작을 설명한 뒤 반드시 단점/주의점을 "하지만~"으로 짚는다.
- **적합 상황 정리**: 각 방법 끝에 "이 방법은 ~에 적합하다"로 언제 쓰면 좋은지 정리.
- 동시성 vs 병렬성처럼 **개념을 먼저 분리**하고 들어간다.

## 마무리
- 핵심 포인트를 **bullet로 요약**.
- **짧고 담백한 소감** 한두 문장. 과도한 감상·미사여구 없음.

## frontmatter
```yaml
---
slug: english-kebab-slug
title: 한국어 제목 - 부제
authors:
  - haeyoung
tags: [English, Tags, Only]   # 태그는 영어
---
```
- 폴더 경로: `blog/YYYY-MM-DD-슬러그/index.md` (이미지는 같은 폴더).
- **title은 한국어, tags는 영어.**

## 윤문(다듬기) 세부 규칙
윤문은 "다시 쓰기"가 아니라 "다듬기"다. 다음만 손본다:
1. **맞춤법·띄어쓰기 교정**: "할수있다"→"할 수 있다", "이방법은"→"이 방법은", "오산이였다"→"오산이었다".
2. **군더더기·중복 제거**, 늘어지는 문장 분리.
3. **흐름·연결 개선** (접속·문단 순서), 평서체로 톤 통일.
4. 어색한 번역투·구어체를 자연스러운 평서체로.
- **금지**: 내용 추가/삭제, 사실·수치·코드 변경, 주장 왜곡, 과한 미사여구·이모지 삽입.
- 코드 블록 안은 건드리지 않는다(명백한 오타 제외, 이때는 따로 알린다).
- 크게 바꾼 부분이 있으면 **무엇을 왜 바꿨는지** 끝에 간단히 요약한다.

## 에세이(Insight)일 때
- TECH보다 **더 담백하고 개인적인 평서체**. 코드 없이 생각·경험 위주.
- 과한 교훈·결론 강요 없이 여운을 남긴다.

## 체크리스트 (작성·윤문 후 확인)
- [ ] 도입이 실무/개인 상황에서 시작하는가
- [ ] 코드가 설명보다 먼저 나오는가 (TECH)
- [ ] 관련 이미지(가능하면 직접 캡처)를 넣었는가 · 출처/저작권은 문제없는가
- [ ] "하지만" 패턴으로 단점/주의를 짚었는가
- [ ] 기술 용어를 백틱으로 감쌌는가
- [ ] 띄어쓰기·맞춤법이 깔끔한가
- [ ] 마무리가 짧고 담백한가
- [ ] 저자 목소리·의도가 보존됐는가
